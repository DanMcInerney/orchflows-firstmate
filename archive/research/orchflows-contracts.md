# Orchflows contracts and integration friction

Research refreshed September 13, 2026 (America/New_York), against the full source copy at [`.sources/orchflows`](../.sources/orchflows), commit [`0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a`](https://github.com/DanMcInerney/orchflows/tree/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a), manifest version 0.7.0. The previous assessment's `86aabd91071fa07a05cf970db2e73909184a1955` remains the baseline. This is source inspection and fetched primary documentation, with proposed designs explicitly marked below. No FirstMate worker was launched for this document, and no installed host configuration was changed.

**Principal finding:** a useful manual integration can supply an entire pinned core and selected library roots in the FirstMate task brief. Orchflows already permits that resolution route. Native plugin registration is a separate distribution convenience and discovery contract; it need not become the first experiment's critical path. Native delegation, delivery policy and actual worker access still require verification.

## Composition and native depth

Orchflows is instructional composition. Loading a workflow applies it in the current context; only its Work and Review primitives create native children. It has no execution engine to connect to FirstMate and no workflow-state service to restart. Work creates a fresh maker; Review creates an independent fresh reviewer who does not repair or delegate repairs. The dynamic workflow joins results, reviews once and allows one repair pass without another review. [Architecture](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/architecture.md#L3-L10), [Work](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/skills/orch-work/SKILL.md#L6), [Review](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/skills/orch-review/SKILL.md#L6), [dynamic composition](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/skills/orch-dynamic-workflow/SKILL.md#L6-L8).

Nested workflow names therefore do not imply nested agents. In the inspected social-search example the coordinator remains in the caller's context, invokes each search leaf there, and receives handles for deferred gathering. Each collection leaf creates one maker and explicitly tells that maker to work without children. Ranking creates one reviewer under the same restriction. This is an existing flat composition with N makers and one reviewer. [Coordinator](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/example-workflows/social-search/skills/social-search/SKILL.md#L6-L18), [collection leaf](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/example-workflows/social-search/skills/search-site/SKILL.md#L6-L12), [ranking leaf](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/example-workflows/social-search/skills/rank-evidence/SKILL.md#L6-L12).

**Proposal:** the ordinary crewmate loads the selected composition itself and owns all primitive calls. Begin with one native child layer and a declared maximum of concurrently active children. Do not wrap the entire composition in Work unless the extra depth is intentional. Permit additional depth only for a workflow whose actual assignments need it. This preserves unchanged core primitives and makes steering, joins and ownership easier to inspect.

**Refreshed host documentation:** the live Claude page contradicts stale search excerpts claiming subagents cannot spawn children. It currently documents three layers by default, controlled by `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`; `1` disables nesting. It records different earlier defaults. It separately documents `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20, with exceptions for resumed agents, forks and certain modes. These claims are not runtime evidence for the installed FirstMate worker. [Claude nesting and limits](https://code.claude.com/docs/en/subagents#let-subagents-spawn-their-own-subagents).

Current official Codex documentation describes subagents in local clients, default enablement, sandbox inheritance and an open-thread limit excluding the primary. It does not establish a FirstMate launch profile's actual native tools or a tested depth bound here. [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference#configtoml).

## Package identity, paths and discovery

Three resolution routes are part of Orchflows' architecture: native skills, supplied package roots, and the home CLI. The outer entrypoint resolves dependency and guidance paths once and passes them through unchanged; composed calls extend context only for new dependencies. Guidance walks dotted prefixes from general to specific, reading core then selected libraries in caller order, and deduplicates paths by first use. An explicitly selected missing domain blocks dependent work. [Resolution contract](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/architecture.md#L40-L52).

| Route | What it buys | What remains unresolved |
| --- | --- | --- |
| Native installed plugin | Namespaced invocation and discoverable skill descriptions using normal host UX | Worker-visible home, registration, enabled state, cache revision, session refresh and competing core installations |
| Full package at an explicit root | Existing contract; exact input bytes can be frozen without installing into a user's active catalog | The brief must select the entrypoint, all dependencies must remain available, and actual native tools must exist |
| Resolve from a managed home | Small JSON interface returns package name/version and absolute resource paths | Resolves mutable current state; does not pin versions, install dependencies or prove host readiness |
| Copy skill folders alone | Small copy | Breaks package-relative docs, guidance and shared references; reject this packaging shape |

The inspected core ships `plugin.json`, both host-manifest directories, `skills`, `guidance`, `docs`, `scripts`, README, agent instruction files and LICENSE. `CORE_ENTRIES` is authoritative. Tests and examples remain in the checkout; optional libraries are separate full packages. Copying the entire repository for research and copying the complete deployable core for runtime are different operations. [Shipped entries and filtering](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/orchflows.py#L25-L27), [file copy rules](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/orchflows.py#L80-L109), [host loading](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/hosts.md#L5-L25).

**Observed session distinction:** this research session exposes installed `orchflows-light` 0.6.3 skills. Read-only inspection of that supplied cache's root/native manifests and dynamic skill found package name `orchflows-light` and the same unqualified `orch-work`, `orch-review`, and `orch-dynamic-workflow` names/descriptions used by inspected `orchflows` 0.7.0. The installed Light skill coordinates this research; it is not evidence that source 0.7.0 is installed, discovered, or executed by a FirstMate worker. The observation does not establish a public commit for those cache bytes.

**Proposal:** record package name, content identity, selected entrypoint and resolved root in every readiness receipt. Use an explicit namespaced identity or pinned path, and keep one enabled core for a native-plugin trial, as upstream instructs. A successful bare-name invocation is insufficient evidence of which core was used. Following a path does not claim registration. Do not silently disable the user's existing Light installation to resolve a collision. [Native identity and refresh](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/architecture.md#L66-L82), [one enabled core](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/hosts.md#L5-L15).

## Freezing a task's entire input package

The existing resolver validates a library name, searches manifests, rejects duplicates, checks containment and returns paths plus an unverified runtime path. It accepts no requested version and emits no content digest. Root manifest validation extracts only name and nonempty version. `doctor` checks required core paths, runtime files, library manifests/skills and generated catalog text; it does not load a worker, check native delegation, validate model choices or install library requirements. [Resolver](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/orchflows.py#L295-L326), [doctor](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/orchflows.py#L329-L355), [manifest validation](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/orchflows.py#L58-L70).

**Proposed task record, not an existing API:**

- Task/attempt identity, selected composition, delivery mode and review scope.
- Complete core and selected libraries: package names, manifest versions, source revisions where available, and content digests for the actual shipped bytes.
- Dependency inventory, entrypoint paths relative to each package, selected guidance domains and ordered resolved relative paths.
- Host-local mapping from retained package identities to absolute roots, plus required tools/runtime dependencies and their readiness outcome.
- Caller model/effort choices by assignment, child count/depth bounds, allowed workspace/output roots and completion route.

Keep reusable records portable by storing relative resources and content identities; resolve host-local absolute roots at launch and supply those absolute paths to agents. Core and every selected library must be retained together. Pinning core alone still permits changed library guidance, scripts or references. A SemVer string alone is insufficient because different source commits can retain the same manifest version.

The important path discipline is: resolve dependencies once **from the frozen bundle**, then pass the resulting context unchanged. A nested composition must not run `resolve` against the mutable default home to reacquire an already resolved package. If a genuinely new dependency is needed, either it exists in the task's recorded bundle or the task pauses dependent work pending an explicit bundle revision and new receipt. Pinning packages does not pin external services, credentials, tools or models.

Library dependencies are prose in README and `references/library-context.md`, not a machine-resolved lock graph. For example, social-search declares required core primitives and optional `research-acquire`; absence of the optional reader can leave another valid acquisition route. Short-video also needs creation and inspection capabilities beyond the core. The first release should admit a small known dependency set and review its transitive references; arbitrary automatic graph discovery would be additional engineering. [Library requirements](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/architecture.md#L66-L89), [social-search context](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/example-workflows/social-search/references/library-context.md#L3-L9), [short-video context](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/example-workflows/short-video/references/library-context.md#L3-L7).

## Upgrade and rollback mechanics

Existing setup stages a new package, renames the previous core, replaces the destination and restores the previous core if the replacement fails. After successful replacement it deletes the previous copy. Later catalog/runtime/host-configuration problems can still yield a partial setup result. Thus the existing backup is failure recovery during the swap, not a retained version store or whole-install transaction. [Swap implementation](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/orchflows.py#L112-L137), [setup ordering and partial result](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/orchflows.py#L220-L271).

Setup preserves an existing example-library destination instead of updating it. It generates both catalogs but does not register or refresh native plugin installations. Running setup from the installed core reuses that core; it does not fetch a release. The dependency-free home runtime likewise does not install optional library dependencies. [Home operations](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/home.md#L21-L53).

**Proposal:** stage a retained bundle for new tasks, validate it, then change the profile's default bundle identity. Existing tasks retain their recorded identities and roots through relaunch. Rollback selects an earlier retained bundle for new tasks; garbage collection waits until no live or resumable task refers to it. A per-task copy is simplest to understand but duplicates bytes; a shared content-addressed store reduces copies but needs reference tracking. Either is additional integration behavior, not a promise of current setup. Native plugin caches should be treated as discovery copies until their exact refresh and retention behavior is verified; an explicit frozen root should own task inputs.

## Models, concurrency and resources

Orchflows resolves model and effort independently. Current caller choices override saved workflow choices; named assignments beat operation defaults within either source. Unspecified controls stay unset. Repairs must honor their own settings, using a fresh worker when continuation cannot. Unsupported combinations are reported before dependent work; prompt text alone cannot select a model. [Assignment contract](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/architecture.md#L32-L38), [host controls](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/hosts.md#L27-L38).

An upstream report describes explicit-path Codex trials observing different maker, reviewer and fixer model/effort pairs in native records. It explicitly leaves Claude execution, omitted controls, configuration overrides and unsupported settings unexercised. This is upstream-reported trial evidence, not a trial run by this investigation and not a FirstMate result. [Reported execution and limits](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/reports/model-effort-implementation-2026-09-13.md#L23-L52).

The source installer writes Codex `agents.max_threads` and Claude `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY`, default 15, to both hosts' user settings. The latter controls parallel read-only tools and subagents; it is distinct from the newer concurrent-subagent/depth controls described above. `--skip-host-config` avoids these writes. Do not interpret setup's `15` as a fleet-wide resource budget. [Written keys](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/host_config.py#L15-L16), [configuration locations](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/scripts/host_config.py#L76-L92), [Claude environment variables](https://code.claude.com/docs/en/env-vars).

**Proposal:** begin with a small task child allowance and one layer, preserve existing host settings, and validate the actual profile's effective settings. FirstMate chooses the outer worker; Orchflows resolves inner assignments. The rough simultaneous-agent upper bound for W workers with C active children each is W × (1 + C), before supervisors or other delivery agents. Aggregate cost and recursive fan-out require separate accounting. A prompt budget is not a hard host-enforced limit. Reject or explicitly reroute an incompatible profile rather than silently losing the selected workflow or substituting model settings.

## Recovery and evidence

The core history reader is read-only. It does not resume agents or prove current liveness. Codex discovery depends on native SQLite indexes; delegation bodies may be unavailable, malformed tails remain gaps, and a missing result means unknown outcome. An outer FirstMate restart cannot infer safe inner replay merely from the presence of old transcript files. [History limits](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/docs/history.md#L3-L29).

There is a useful existing design in the optional Evolve library: sole coordinator ownership of a journal/checkpoint, immutable candidate identities, native handles recorded before waiting, results recorded before judging, and reconciliation before retry. It explicitly blocks a slot when liveness is unknown and forbids two coordinators over the same run directory. This is documented workflow behavior, not an implemented general recovery subsystem. [Evolve state](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/example-workflows/evolve/skills/evolve/references/state.md#L3-L22).

**Proposal:** reuse those minimal concepts in the compatibility composition: parent attempt, child handles/assignments, exact outputs, joined candidate identity, steering epoch, current phase and pending delivery action. Recovery either rejoins demonstrated-live children or confirms they stopped before restarting interrupted assignments. Unknown liveness blocks replacement dispatch. Stale steering invalidates affected work/review evidence. Persist only enough state for the chosen simple composition; do not port the full Evolve search journal into every task. The crewmate remains the sole FirstMate completion sender.

## Distribution facts and smallest useful scope

The inspected Orchflows root contains an MIT LICENSE naming Dan McInerney; the file includes notice-retention terms. The copied `research-acquire` and `social-search` libraries have separate LICENSE files. `git ls-files '*LICENSE*' '*CONTRIBUTING*' '.github/*'` returned these three license paths and no tracked CONTRIBUTING or `.github` paths at this revision. This inventory is not a legal compatibility conclusion or evidence of maintainer acceptance. Preserve notices and check each selected library's actual files before distribution. [Root license](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/LICENSE), [research-acquire license](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/example-workflows/research-acquire/LICENSE), [social-search license](https://github.com/DanMcInerney/orchflows/blob/0fc6cb7ac7da7b275a83cc90807fba15b8ceb15a/example-workflows/social-search/LICENSE).

The best small integration hypothesis is an optional compatibility composition in an ordinary crewmate, backed by a generic FirstMate task-profile/brief seam and retained package inputs. A manual spec can investigate that boundary before implementing the seam. Keep the existing Work/Review contracts. A distinct work-only composition may hand off to the existing delivery gate; a composition containing independent review needs the corresponding explicit task policy. Guidance-only use remains a smaller alternative if native delegation is unavailable, but should be labeled as that reduced product. A fleet-backed adapter changes the primitive execution contract and deserves a separate comparison rather than being hidden inside a plugin installer.

The decisive remaining probes are actual worker tool/path visibility; selected-package identity under competing installations; a flat native maker/reviewer run; effective model settings and limits; steering/cancellation; recovery without duplicate work; and old-task relaunch after a new bundle becomes the default. Package tests and source inspection cannot close those runtime gaps.
