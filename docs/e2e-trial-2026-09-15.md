# End-to-end trial: a mixed-model workflow through stock FirstMate

Started September 15, 2026. This trial exercises the FirstMate-native library
on a real FirstMate checkout with real Herdr workers. Nothing in FirstMate is
patched. The Claude Code session that ran the trial acted as the FirstMate
primary: it read the skills and applied them with FirstMate's own owners
(`fm-brief.sh`, `fm-spawn.sh`, `fm-crew-state.sh`, `fm-send.sh`,
`fm-merge-local.sh`, `fm-teardown.sh`). Whether a FirstMate primary session
run by a model follows the skills the same way is the one thing this trial
cannot show; everything below the primary is FirstMate's real behavior.

## Environment

| Item | Value |
| --- | --- |
| FirstMate | `b182d0f908b78d08c7ccb8dce3775bdca8c5d657`, unpatched clone at `/tmp/orchflows-e2e/firstmate` |
| FirstMate home | `/tmp/orchflows-e2e/home` (`FM_HOME`), `FM_ROOT_OVERRIDE` to the clone |
| Backend | Herdr 0.7.4, private lab session from `fm-herdr-lab.sh` |

## Design

The trial has two halves, both driven by the skills.

**Half A, build a workflow (orch-build-workflow).** One Work ship on
`orchflows-home` authors a library `mixed-build` with one manual-only workflow
`feature`. One fresh Review scout audits the library against the `orchflows`
and `writing` Review guidance. One repair pass by steer. FirstMate lands the
branch with `fm-merge-local.sh`; setup regenerates the catalogs.

The `feature` workflow has three phases, each one Work, one Review and one
repair pass, with the maker and reviewer always from different vendors:

| Phase | Work | Review |
| --- | --- | --- |
| spec | scout, codex `gpt-5.6-luna` xhigh | scout, claude `claude-sonnet-5` xhigh |
| implement | ship, claude `claude-sonnet-5` xhigh | scout, codex `gpt-5.6-luna` xhigh |
| docs-qa | ship, codex `gpt-5.6-luna` xhigh | scout, claude `claude-sonnet-5` xhigh |

Those preferences are saved beside the assignments in the workflow, as
architecture.md prescribes. The library also supplies a `code.cli` guidance
extension so the trial exercises guidance layering.

**Half B, use the workflow (the trial that build-workflow requires).** Run
`mixed-build:feature` by name on `kvlog`: build a structured-log summary CLI.
Every phase is reviewed by the other vendor, the final docs-qa Review checks
the delivered artifact against the spec's acceptance checklist, and each
phase lands through `fm-merge-local.sh` before the next starts.

## Expected observations

- Every agent is a FirstMate task with its own `state/<id>.meta` recording the
  requested harness, model and effort, its own Treehouse worktree, and its own
  Herdr tab in the lab session.
- Review scouts check the candidate out detached and write findings only.
- Repairs arrive through the steering inbox and the maker updates its branch.
- The workflow phase and task IDs live in the backlog item note.
- Landing is FirstMate's fast-forward merge; teardown refuses unlanded work.

## Evidence

Filled in as the trial proceeds.

### Half A

**Author Work `orch-author-1`** (ship, local-only, `--harness claude --model claude-sonnet-5 --effort xhigh`). FirstMate recorded exactly that profile in `state/orch-author-1.meta`, allocated Treehouse worktree `~/.treehouse/orchflows-home-1fccc7/1/orchflows-home`, opened Herdr tab `w1:t2` in the lab session, and moved the backlog item to in flight.

The first launch died within four seconds: the busy-state record showed a Claude `session-end` hook at spawn+4s, the tab held a bare shell, and the scrollback had been cleared, so the cause is unrecorded. `fm-control.sh orch-author-1 relaunch` recovered it without any manual work in the tab: the pane then showed Claude Code 2.1.272 "Sonnet 5 with xhigh effort" in the task worktree with the launch brief as its prompt, and `fm-crew-state.sh` reported `working · harness busy (claude-hook)`. The worker created `fm/orch-author-1` and began reading the core docs named in its brief. It finished in about eight minutes with one commit (`79b2d6c`, nine files, 121 lines): manifests, README, `guidance/code.cli.md`, `references/library-context.md`, `skills/feature/SKILL.md` (198-word body, `disable-model-invocation: true`, description beginning "Manual:"), and trial materials. The captain's own checks passed: `resolve mixed-build --skill feature` found the skill in the worktree, and the phase table matched the requested vendor alternation exactly.

**Review scout `orch-author-review-1`** (scout, fresh Sonnet xhigh; the dispatch rule names Codex luna for reviews, but Codex was unusable in WSL because its refresh token had been consumed elsewhere, so the captain overrode the model and wrote the reason in the backlog note). It launched cleanly, checked the branch out detached in its own worktree (`~/.treehouse/orchflows-home-1fccc7/2/orchflows-home`), applied the `orchflows`, `writing` and `code` Review sections, ran `resolve` and `doctor` itself, passed the captain-hold completion gate with `--none`, and returned in five minutes: **ready with repairs**. Findings, by its own ordering: (1) no trial record, which is exactly what Half B produces and was deferred; (2) the spec phase omitted `code.cli` guidance that its own expected behavior assumes; (3) the acceptance checklist was named as input to the docs-qa Review but not the docs-qa Work; (4) the Codex-side manual-only description lacked the exact trigger phrase; (5) root `plugin.json` mirrored the Claude manifest rather than the Codex one; (6) the body sat at 198 of 200 words. It also confirmed every static check passed and that the skill composes the primitives by name without restating them.

**Repair pass.** Findings 2 through 5 went back to the author as one steer through FirstMate's durable inbox (`fm-send.sh`), with finding 1 explicitly deferred. The author's Claude session was still alive at its prompt, acknowledged the message (`001.msg` moved to `handled/`), and two minutes later appended a fresh `done: ready in branch fm/orch-author-1`. Its repair commit `5d13f33` touched four files: `code.cli` added to the spec phase's Work and Review guidance, the checklist named as input to both docs-qa agents, the description ending with the exact trigger phrases, root `plugin.json` now identical to the Codex manifest. Body 195 words; manifests agree; worktree clean. No second review was requested.

**Landing.** `fm-merge-local.sh orch-author-1` fast-forwarded the home's `main` from `75c1b5e` to `5d13f33`. Rerunning `scripts/orchflows.py setup --home <home>` regenerated both catalogs with `mixed-build` listed, and `resolve mixed-build --skill feature` returned the installed skill path. Both tasks were torn down through `fm-teardown.sh`, which released their Treehouse slots and Herdr tabs and closed the backlog items.

Three captain-side stumbles worth recording, none of them FirstMate defects:

- The first merge attempt was refused because the project held an untracked `.orch/friction/` log. It was written by one of the operator's global Claude Code plugins from inside the author's session, and it recorded that the worker's first `git commit` failed with "Author identity unknown" (no `user.name` in the WSL environment) before the worker set one itself. The log was archived and removed; a real primary would see the same refusal.
- Every teardown was refused with "cannot resolve the shared Treehouse project lock" until the owners were run from the FirstMate home. The captain's shell had inherited a Windows worktree as its working directory, whose `.git` pointer is a Windows path, and FirstMate's lock resolver hashes the origin URL with a bare `git hash-object` that failed there. A real primary runs from its home and never hits this.
- The captain ran `setup` without `--home` once, which created an empty `~/.orchflows-firstmate` in the operator's WSL home; it was removed. `docs/home.md` already says the home is never the current directory; the helper now always passes `--home`.

### Half B

Half B paused once on Codex authentication: `codex login status` in Ubuntu said "Logged in using ChatGPT" while every request failed with "refresh token was already used", because another client had consumed the WSL token pair. The operator ran `codex login`, after which `codex exec --model gpt-5.6-luna` answered and the interactive pane resolved Codex 0.154.0. The six phase briefs are saved under [e2e-2026-09-15/briefs](e2e-2026-09-15/briefs/) with placeholders the captain substitutes at dispatch; the workflow's own backlog item `kvlog-feature` carries the phase note.

**spec Work `kvlog-spec-1`** (scout, `--harness codex --model gpt-5.6-luna --effort xhigh`, the workflow's saved preference). FirstMate launched `codex --model 'gpt-5.6-luna' -c 'model_reasoning_effort="xhigh"'` in Treehouse worktree `~/.treehouse/kvlog-0f3c59/1/kvlog` on tab `w2:t2`. Two first-run dialogs then needed the captain, exactly as FirstMate's captain contract anticipates ("handle any trust dialog through harness-adapters"): the repository trust prompt, answered with one `fm-send.sh --key Enter` as the Codex adapter documents; and a second prompt the adapter (written against Codex 0.152) does not know, Codex 0.154's "Hooks need review: 4 hooks are new or changed" for the per-task busy hooks FirstMate writes into the worktree, answered "Trust all and continue" from the tab. FirstMate's live classifier reports Codex as `unknown (codex-unverified)`, so supervision of Codex workers here rested on the status log, which the worker kept current (`working: inspecting the repository and preparing the design report`, then `done: design report and acceptance checklist are complete`). Elapsed about 20 minutes including the two dialog waits. The report (2,455 words) gave a complete CLI contract with exact JSON and human output shapes, a one-module layout with named functions, eight edge-case rules, a 15-test plan, and a 13-item acceptance checklist of shell commands with exact expected output. The scout also mentioned following an `orch-investigate` lane, a skill from the operator's globally installed Codex skills rather than from this library; the brief did not ask for it and it did not change the deliverable.

**spec Review `kvlog-spec-review-1`** (scout, `claude claude-sonnet-5 xhigh`, the saved preference; a different vendor from the maker). It read the spec and the three guidance files, re-derived every number in the spec's worked fixture, tested the `fromisoformat` `Z` claim on the local interpreter, confirmed all captain requirements present, and returned in six minutes: **ready with eight repairs**. The substantive ones: exit-1 and exit-2 diagnostics pinned for only two of their several classes; the `<stdin>` label used in tests but never stated in the contract; no minimum Python version despite relying on 3.11-only `Z` parsing; a checklist item pinning the exact unit-test count; one item without a self-contained expected result; the `by_service` zero-omission rule shown but never stated; no fail-fast rule across sources. The captain sent all eight plus a hash typo back to the Codex scout as one steer.

**spec repair.** The Codex scout's session was still alive at its prompt. It acknowledged the inbox record, revised the report in place (2,455 to 2,957 words, acceptance list 13 to 17 items, `<stdin>` label and message templates in the contract, `Z` normalization with a 3.9 floor, `by_service` rule stated, fail-fast across sources stated, typo fixed) and appended `done: spec revised per review` three minutes later. No second review. Both scouts were torn down; their reports survive under `data/<id>/report.md` as FirstMate documents, and the implement phase reads them from there.

**implement Work `kvlog-impl-1`** (ship, local-only, `claude claude-sonnet-5 xhigh`, the saved preference). Launched cleanly into the reused Treehouse slot on tab `w3:t2`, given the spec and its review by path. In about nine minutes it committed `dd1d4b2`: `kvlog.py` (251 lines), `tests/test_kvlog.py` (309 lines, the spec's 15 named tests), `tests/__init__.py`, and a project `AGENTS.md` that FirstMate's own ship brief asks workers to seed. The captain's read-only checks in the worker's worktree: `python3 -m unittest` ran 15 tests OK, and a one-record `--json` run produced the spec's exact shape.

**implement Review `kvlog-impl-review-1`** (scout, `codex gpt-5.6-luna xhigh`; the other vendor again). No first-run dialogs this time: the repository trust and hook acceptance from the spec scout persisted, exactly as the Codex adapter reference says, so the second Codex worker started unattended. In ten minutes it checked the branch out detached, ran the suite (15 OK), replayed all sixteen code acceptance items with its own fixtures (all pass), then probed beyond the list and returned **not ready** with four findings: `NaN` in an extra field accepted through Python's JSON extension; an `OSError` during stream iteration escaping as a traceback; the README still a stub; and a year-0001 timestamp overflowing UTC conversion and rendering an unpadded year. The README finding is the docs-qa phase's job by the workflow's design, so the captain sent the other three back to the Sonnet implementer as one steer with the instruction to cover each with a test.

**implement repair and landing.** The implementer acknowledged the inbox record and three minutes later committed `d0d0673` (38 lines changed in `kvlog.py`, 69 added in tests; suite now 20 OK). The captain's probes in its worktree confirmed all three: `NaN` in an extra field now exits 1 with `invalid JSON`, the underflowing timestamp exits 1 with `invalid timestamp`, and year 0001 renders `0001-01-01T00:00:00Z`. `fm-merge-local.sh` fast-forwarded `main` `682a53c` to `d0d0673` and both tasks were torn down. Before that could happen, the same untracked `.orch/` plugin log blocked the first merge attempt again; and FirstMate's teardown correctly refused to discard the unlanded implement branch ("commits not yet on main"), which is the guard working as designed.

Two more captain-side stumbles, both mine and both informative:

- The landing helper did not stop when the merge was refused, so the first docs-qa Work (`kvlog-docs-1`) was dispatched onto a worktree based on the old `main`. It was torn down and the helper now stops on a refused merge.
- The second docs-qa Work (`kvlog-docs-2`) also started at the seed commit. Cause: Treehouse returns a slot positioned at the project's local `main`, but spawn's `freshen_spawn_worktree_base` resets any worktree to `origin/main` whenever the project has an origin, and FirstMate's local-only merge advances only local `main` by design. The bare origins were the captain's addition; a FirstMate local-only project has no remote. Both origins were removed, after which slot allocation starts from the merged commit. The retired component engine had built a whole "launch-position owner" for exactly this stale-base case; in stock FirstMate the fix is the project shape.

**docs-qa Work `kvlog-docs-3`** (ship, local-only, `codex gpt-5.6-luna xhigh`, the saved preference). It then reported `all 17 acceptance items and 20 unit tests pass` and `done: ready in branch fm/kvlog-docs-3`, about 27 minutes after launch. The `blocked:` and `resolved:` lines are FirstMate's ordinary status protocol; a model-run primary would have been woken by the watcher for each. Its branch (`ca74410`) added a 131-line README, `ACCEPTANCE.md` with all 17 rows PASS, `examples/app.jsonl`, a 308-line `scripts/acceptance.sh` runner, and one thing that does not belong: a ticket file under `.orch/tickets/` written by the operator's globally installed `orch-task` Codex skill, which the worker committed along with its work.

**docs-qa Review `kvlog-docs-review-1`** (scout, `claude claude-sonnet-5 xhigh`; the final QA of the delivered artifact by the other vendor). In five minutes it checked `ca74410` out detached, re-ran the committed acceptance runner (17 PASS, exit 0), re-ran the three README commands and nine README greps (all output byte-identical to what the README shows), ran the suite (20 OK), tried three novel inputs plus a boundary case (all correct per the spec), confirmed `kvlog.py` and the tests are byte-identical to `main`, and returned **ready with one repair**: the README's usage section hid the simple invocation behind a scratch-directory setup that exists only to satisfy the acceptance greps. It noted, without objecting, the `.orch/tickets/` file in the diff; the captain added its removal to the repair steer, together with the reviewer's small test-message note.

**docs-qa repair and landing.** The Codex worker acknowledged the steer, committed `c08cb11` five minutes later (README usage now leads with `python3 kvlog.py examples/app.jsonl` and its real output, the `.orch/` file removed from the branch, the repeated-`-` test pinned), and reported the runner and suite green. The captain confirmed in its worktree: 20 tests OK, 17 PASS, clean tree. The project root again held a fresh `.orch/` log from the reviewer's session; archived and removed. `fm-merge-local.sh` fast-forwarded `main` `d0d0673` to `c08cb11`; both tasks were torn down; every Herdr tab in the lab is closed.

**Final verification on `main`** by the captain, read-only: `python3 -m unittest` 20 OK; `bash scripts/acceptance.sh` 17 PASS; `python3 kvlog.py examples/app.jsonl` prints the documented summary; working tree clean. The delivered artifact, the four reports, the backlog and the steers are copied under [e2e-2026-09-15](e2e-2026-09-15/).

## Summary

| | Agents | Repairs | Landings | Wall clock |
| --- | --- | --- | --- | --- |
| Half A (build the workflow) | 2 (Sonnet, Sonnet) | 1 steer | 1 | about 25 min |
| Half B (run it on kvlog) | 6 (luna, Sonnet, Sonnet, luna, luna, Sonnet) | 3 steers | 2 | about 2 h 20 min, including two discarded dispatches and four dialog or block waits |

Everything the plan promised happened through stock FirstMate: each agent was a FirstMate task with the requested harness, model and effort in its metadata, its own Treehouse worktree and Herdr tab; reviewers checked candidates out detached and returned findings only; repairs arrived through the steering inbox; phases landed through the local merge owner; teardown refused unlanded work until it landed; the backlog item carried the phase and task IDs throughout. Every reviewer was the other vendor from its maker, and each of the three implementation-level reviews found something real: eight spec gaps, three code defects outside the checklist, one README structure problem plus a foreign file.

## Gaps and lessons

- A model-run FirstMate primary has not been shown to follow these skills; the captain here was the Claude Code session that ran the trial. The briefs it wrote are in `e2e-2026-09-15/briefs/` and are the best evidence of what the skills need a primary to say.
- Callers must give a local-only project no origin remote, or FirstMate's spawn freshens new worktrees from a base the local merge never advances. `docs/firstmate.md` should say so.
- FirstMate's Codex adapter is pinned to 0.152 and does not know 0.154's hooks-trust prompt; Codex workers in this WSL environment cannot pass backticks through their exec wrapper. Both are FirstMate or environment facts, not library defects, but a primary must expect the corresponding `blocked:` lines.
- The operator's globally installed Codex and Claude skills wrote `.orch/` state into worktrees and project roots during three tasks; one file reached a commit. A trial environment should run workers without unrelated global plugins, or projects should ignore `.orch/`.
- The first author launch exited within four seconds for a reason the tab did not retain; FirstMate's relaunch recovered it.
- The WSL environment lacks a global git identity, so workers set their own; a real home would configure one.
- Delivery modes other than local-only were not exercised.
