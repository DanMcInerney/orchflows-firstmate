# FirstMate contracts and integration seams

Research date: September 13, 2026 (America/New_York). Source inspected: FirstMate [`b182d0f908b78d08c7ccb8dce3775bdca8c5d657`](https://github.com/kunchenguid/firstmate/tree/b182d0f908b78d08c7ccb8dce3775bdca8c5d657). `git rev-parse HEAD` and `git status --short` confirmed that revision and a clean research checkout. This is source inspection and design reasoning; no FirstMate initialization, live workers, lifecycle commands, integration code or new tests were run for this document. Upstream agent instructions are evidence about FirstMate behavior, not instructions governing this investigation.

The most useful existing seam is the durable task brief's `## Firstmate spec`. A dependable automatic integration should additionally resolve a worker workflow before launch, preserve its identity across recovery, and reconcile it with the delivery stage. The current source provides useful mechanisms for these changes, but does not already provide an Orchflows workflow attachment API.

## Q04: attachment and durable instructions

**Observed source behavior.** `fm-brief.sh` creates separate `## Captain's intent` and `## Firstmate spec` sections. Spawn rejects placeholder-only or empty sections, then copies the original brief into `launch-brief.md`, appends the current worker-role contract, and appends the no-mistakes intent overlay when applicable. This rendering also runs for relaunches. [Scaffold](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-brief.sh#L348-L355), [validation and overlay](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-spawn.sh#L2350-L2389).

The source brief is the durable input; the launch overlay is regenerated output. A manual trial can put the selected workflow, complete package root, libraries, allowed child operations and required result in the Firstmate spec. Editing only `launch-brief.md` would lose that addition at relaunch. Putting bridge instructions in captain intent would also misrepresent their provenance: no-mistakes receives captain intent and later captain words, and explicitly excludes the Firstmate spec and the worker's own decisions. [Intent contract](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-dod-lib.sh#L217-L232).

**Recommendation.** Use the existing spec for a manual proof. For automatic attachment, add a generic, opt-in worker-workflow resolver to FirstMate's existing launch owner. Keep resolved identity separate from generated prose; render a bridge block alongside current role/delivery overlays. The block should reference a complete, retained package version, not a mutable plugin-cache location. Preserve the source brief's captain/spec distinction. A separate Orchflows library can own workflow composition and FirstMate-specific guidance; FirstMate should own dispatch, launch validation, stage and delivery authority.

**Counterexample: scout promotion.** Promotion writes a separate `ship-instructions.md`, changes metadata from scout to ship, and instructs the live worker that the scout-time Firstmate spec is investigation context rather than ship-time instructions. It prints the command to send those instructions; it does not replace the original brief. Meanwhile, ordinary spawn/relaunch selects `brief.md`, and the control plane appends its progress note there. An Orchflows workflow selected solely by the scout spec cannot simply be assumed to remain the right ship workflow after promotion. This is a source-derived replay hazard, not a reproduced runtime bug. [Promotion instructions and metadata](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-promote.sh#L166-L217), [brief selection](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-spawn.sh#L2329-L2337), [relaunch note source](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-control.sh#L789-L802).

The first trial should exclude promotion. A later design should make promotion an explicit workflow/stage transition and ensure replacement workers replay the accepted ship instructions, including already handled steering that changed the task.

## Durable task metadata: a seam, with limits

**Observed source behavior.** Spawn writes task identity, workspace, project, harness, kind, delivery mode, merge posture, model, effort and incarnation fields. On relaunch, `preserve_relaunch_meta` retains every prior line whose key is outside its declared owned-key list. Thus an unknown workflow identity field survives this relaunch path. Promotion likewise replaces only `kind`, `mode` and `yolo`, retaining other lines. [Metadata publication and preservation](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-spawn.sh#L3868-L3944), [promotion rewrite](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-promote.sh#L196-L208).

This supports extending metadata deliberately; it does not establish an authorized external writer, validation contract, ownership convention or preservation guarantee across every metadata mutation. Do not implement a background wrapper that appends fields after launch: the task can run before attachment, and unsynchronized writes can race the lifecycle owner's locked publication.

**Proposed contract.** Persist a small resolved descriptor reference/digest with schema, selected workflow/library revisions, capability requirements, delivery stage, review policy and fallback policy before launch. Store detailed checkpoint/results separately. Let the launch transaction publish both consistently. A task's `spawn_gen` distinguishes outer incarnations; use it in inner checkpoint evidence, while recognizing that writing the generation into a file does not itself fence an old native child from editing.

**Future acceptance probes.** Verify unknown-field preservation through ordinary relaunch, harness change, promotion and failed-launch rollback. Separately test the proposed supported workflow fields. Update a global default between initial spawn and relaunch: the existing task must retain its resolved package and policy, while a new task may receive the new default. A changed mandatory FirstMate role/delivery contract must still apply, or refuse the incompatible pinned workflow explicitly.

## Q05–Q06: workspace and role boundaries

**Observed source behavior.** Ship workers must verify their assigned worktree and modify nothing outside it; their named branch is `fm/<id>`. Scout workers may make scratch changes and commits, but only the report and status file are explicitly allowed outside the worktree. Native children therefore inherit a narrower assignment than a general workflow authoring or multi-worktree composition might assume. [Ship setup/rules](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-brief.sh#L457-L479), [scout setup/rules](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-brief.sh#L371-L399).

For FirstMate self-development, the appended current-role contract explicitly says to do the assigned work oneself and not delegate the task. It supersedes earlier brief instructions about role/identity. A generic native-child exemption elsewhere does not remove this specific conflict. [Current role contract](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-dod-lib.sh#L31-L39).

**Recommendation.** Start with read-only children for a report task in a different repository. For a coding trial, use one writer at a time in the assigned worktree, and collect/stop that writer before review or parent edits. Parallel non-overlapping edit assignments are still vulnerable to shared Git-index/branch operations; directory partitioning alone is insufficient. Additional child worktrees need explicit roots, branch ownership, integration, disposal and interruption handling agreed with FirstMate.

Treat FirstMate self-development as unsupported for native delegation until its single role-contract owner adopts a narrow distinction between bounded subordinate work and fleet supervision. Do not try to override the last-appended role block by adding stronger wording earlier in the spec. Guidance-only local execution remains a possible self-development option, subject to existing contributor requirements.

## Q07: recovery and cancellation are distinct from durable results

**Observed source behavior.** FirstMate relaunch is a new agent in the existing endpoint and worktree, not restoration of a harness session. The control plane requires a progress note for ship/scout tasks and records worktree HEAD plus a dirty yes/no flag. It appends a note to the brief, telling the replacement to check unhandled inbox messages. It does not serialize the prior conversation or native child state. [Documented relaunch contract](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/docs/agent-control.md#L50-L72), [checkpoint implementation](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-control.sh#L695-L727), [note implementation](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-control.sh#L756-L784).

The launch owner requires a positively agent-free recorded endpoint and an existing worktree; only supported recovery-grade backends can satisfy this gate. That endpoint check does not establish that every host-native child or detached command from the old session has stopped. The inspected interrupt path reports cancellation as unconfirmed except when its specific Muse terminal acknowledgment is available. A successful interrupt postcondition otherwise proves the outer agent is still alive, not that all subordinate work ceased. [Relaunch preflight](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-spawn.sh#L1347-L1372), [interrupt claims](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-control.sh#L389-L438).

**Recommendation.** Use restart-from-durable-checkpoint semantics initially. Persist workflow/package identity, accepted task/steering version, phase, child assignments and handles as evidence, observed child outcomes, retained artifacts, candidate revision, pending joins and unresolved decisions. On replacement, treat nonterminal child handles as unknown until the actual host proves whether they are usable and stopped. Never launch a replacement writer merely because the old outer agent is gone. If termination cannot be proven, block or choose an explicitly isolated new candidate whose result cannot be confused with the old one. Even the read-only trial must test cancellation/tool behavior; it only reduces the damage possible while proving it.

The existing HEAD-plus-dirty flag is useful recovery context, but insufficient exact candidate provenance: many distinct dirty trees have the same HEAD and `dirty=yes`.

## Q08: steering, decisions and delivery mapping

**Observed source behavior.** The per-task inbox contains numeric message files; the worker reads and acts in numeric order, then moves each handled message into `handled/`. That move is acknowledgment. Unhandled records survive relaunch; the watcher re-rings or escalates them. This is separate from the captain's `fm-inbox.sh` capture surface. [Brief receive contract](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-brief.sh#L202-L214), [durable message format and re-ring policy](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-task-inbox-lib.sh#L25-L59).

**Proposed mapping.** The crewmate remains the only FirstMate-facing status/inbox owner. Children return findings, questions and results to it. At a steer, the parent first records the changed assignment and applies it to affected children, or stops them; then acknowledges the outer message. Acknowledgment need not wait for the entire new assignment to finish, but must mean it has been accepted and durably applied, rather than merely read. Record which steering sequence each result used so late results from an earlier request cannot silently become current.

Blocking and human decisions require explicit resolution: the generated rules say later `working` or `done` never closes an opened decision/blocker; an exact-key `resolved` line does. Child questions therefore need stable correlation through the parent, without inventing a second human escalation channel. [Status/decision rules](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-brief.sh#L470-L491).

| Outer delivery | Inner boundary before the parent signals |
| --- | --- |
| Scout | Report complete, children joined/stopped, evidence retained, captain-call completion gate satisfied; parent emits report conclusion. |
| Local-only | Integrated candidate committed on `fm/<id>`; parent emits branch ready; merge authority remains outside. |
| Direct-PR | Candidate committed, branch pushed and PR opened through selected delivery path; parent emits full PR URL. |
| No-mistakes implementation | Inner implementation complete and committed; all inner writers stopped; parent emits implementation `done` and waits for FirstMate's pipeline instruction. |
| No-mistakes validation | Parent drives pipeline gates; the pipeline owns fixes. After CI-ready, parent emits the second `done` with PR URL and green checks. |

These boundaries follow the existing definitions of done; they are not a proposal to translate native-child completion events mechanically into status lines. [Delivery definitions](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-dod-lib.sh#L193-L249). The no-mistakes active-run ban on parent hand edits also excludes continuing an Orchflows repair pass while that pipeline runs.

## Q09 and Q14: exact results and non-code retention

**Observed source behavior.** Scouts explicitly support a stand-alone written report at `data/<id>/report.md`, including commands, evidence and recommendations. Their scratch worktree is disposable. Normal teardown requires that report to exist and verifies the captain-call completion gate. The gate inventories unresolved captain decisions from the report and visual review; report completion alone is insufficient. [Scout definition](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-brief.sh#L416-L422), [teardown enforcement](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-teardown.sh#L3110-L3122), [captain-call owner](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/.agents/skills/captain-hold-lifecycle/SKILL.md#L15-L27).

Teardown removes task temporary files, lifecycle journals, harness state and the handled/unhandled instruction inbox. Therefore neither the inbox nor the relaunch journal is a permanent audit store. [Cleanup](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-teardown.sh#L3448-L3466).

**Recommendation.** Research, design and scoped review fit scouts when the report contains the retained deliverable. A result contract should identify package/workflow revisions, assignment and steering version, maker/reviewer identities, exact candidate commit or snapshot manifest, commands actually run, outcomes, limitations and retained artifact locations. A reviewed revision must be invalidated when subsequent edits or rebases change the candidate; report both the reviewed state and final delivered state. Do not claim a pre-no-mistakes review covers changes subsequently made by that pipeline.

Media, slide decks and workflow libraries need more than a report path. A report link to a scratch PNG or editable project does not preserve the target. Either use a ship task whose repository commits contain the durable artifact, or explicitly extend scout output permissions and collection to a retained artifact directory, with a manifest verifying all referenced files exist after teardown. The current brief does not automatically authorize arbitrary files alongside the report. A later authoring task should create a reviewable library package inside its assigned worktree; installing that package into a user's live Orchflows home is a separate authorized delivery step.

## Q11 and fallback: inheritance does not provision a host

**Observed source behavior.** FirstMate's inherited configuration set includes `crew-dispatch.json`, `crew-harness`, `launch-env-allowlist` and several other named files. The primary's value wins at convergence; absence is mirrored. Local and remote transfer owners derive their allowlist from the same declaration, and differing code-root declarations require ordinary synchronization before transfer succeeds. A new workflow config item is not included automatically. [Inheritance owner](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-config-inherit-lib.sh#L29-L69).

When environment filtering is enabled, the launch uses `/usr/bin/env -i` and expands allowed values in the destination pane shell. It does not snapshot those values from the invoking FirstMate process. Thus listing `ORCHFLOWS_HOME` or `CODEX_HOME` only retains an already present destination value; it does not provide one. The launch owner explicitly forwards a set `CLAUDE_CONFIG_DIR` for Claude, which is a useful existing pattern, not proof of general variable forwarding. [Environment implementation](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-spawn.sh#L4069-L4078), [pane-side filtering](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-spawn.sh#L4161-L4179).

**Recommendation.** Inherit logical workflow requirements and version policy, then resolve/provision roots independently on each host. Keep absolute package paths out of shared config. Preflight the actual worker process's resolved home, package bytes, plugin visibility, native tools and model/effort controls. A local complete package path plus explicit spec can reduce discovery ambiguity in the first manual trial; it cannot create native delegation tools that the host lacks.

Ship/scout relaunch normally retains the recorded harness rather than adopting changed crew defaults. An explicitly selected new harness is allowed, and its model/effort must be re-resolved. Consequently capability validation must cover relaunch as well as initial dispatch. [Recorded profile reuse](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/bin/fm-spawn.sh#L1390-L1399), [profile change contract](https://github.com/kunchenguid/firstmate/blob/b182d0f908b78d08c7ccb8dce3775bdca8c5d657/docs/agent-control.md#L58-L63).

A missing required package/tool should refuse the selected workflow. A guidance-only downgrade or another compatible harness is possible only if already authorized by the resolved policy; report the actual reduced mode. Do not relabel ordinary execution as a successful Orchflows workflow.

## Discriminating probes before implementation approval

These are proposed experiments, not executed results:

1. **Attachment persistence:** select a pinned workflow in the original spec; compare initial and relaunched effective instructions; deliberately alter the generated launch overlay and verify it is regenerated. Confirm build guidance never contaminates no-mistakes captain intent.
2. **Metadata and policy persistence:** carry a sentinel extension field through supported lifecycle rewrites, then test an explicitly designed workflow descriptor. Change global defaults and package availability while a task exists; require pinned replay or a clear failure.
3. **Promotion replay:** promote a workflow scout, acknowledge the ship instruction, relaunch it, and inspect the effective task stage/spec. This must fail certification if scout-only constraints silently reappear or accepted ship constraints disappear.
4. **Old-child boundary:** keep a native child active, interrupt/exit/relaunch the outer worker, and observe child liveness and writes. Do not certify automatic replacement writers without demonstrable termination or isolation.
5. **Steering/review freshness:** steer during child execution and during independent review; crash around acknowledgment; ensure the accepted task version and any final candidate match, with duplicate processing harmless and old results rejected.
6. **Artifact teardown:** deliver a report referencing an image and editable source, inspect the retained manifest, then tear down through FirstMate. Verify both referenced files and necessary provenance remain accessible.
7. **Destination environment:** use a pre-existing terminal daemon whose environment differs from the caller; compare absent/empty/populated allowlists and explicit Claude configuration forwarding. Repeat separately on a remote secondmate host with different package paths.

The source closes much of the attachment, inheritance and delivery-shape uncertainty. Actual child capabilities, cancellation, package activation and full lifecycle replay remain runtime gates. Those gaps should constrain the first supported scope rather than be hidden behind a broad compatibility label.
