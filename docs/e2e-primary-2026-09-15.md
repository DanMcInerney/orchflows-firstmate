# Trial: a model-driven FirstMate primary follows the skills

Run September 15, 2026, after [the first end-to-end trial](e2e-trial-2026-09-15.md), whose one open question was whether a FirstMate primary session run by a model follows these skills the way the trial's human-driven captain did. This trial answers it: a stock FirstMate primary on Claude Code, with the package loaded as a plugin, took one plain-language request and ran the dynamic workflow end to end without any Orchflows instruction beyond `captain.md` and the installed docs. Evidence is under [e2e-primary-2026-09-15/](e2e-primary-2026-09-15/).

Two launch flags deserve a note. `--plugin-dir` registers the package for this session only, so the operator's Claude configuration stays untouched. `--setting-sources project,local` drops the operator's user-level Claude configuration, whose global `CLAUDE.md` routes every request through an unrelated skill library; a probe before the trial confirmed the primary then sees exactly the five Orchflows skills plus Claude Code's built-ins, no global instructions, and FirstMate's own project hooks and skills. Workers are launched by FirstMate and did inherit that global configuration, as in the first trial; nothing from it reached the delivered branch this time.

Operator steps, all outside the skills: accept Claude Code's folder-trust dialog for the clone, attach the lab viewer so panes get a 120-column grid, type the request, and answer the primary's merge question. A git identity was exported into the lab server's environment so worker commits would not fail on the missing global identity the first trial recorded; worker panes inherited it, and every commit on the branch carries it.

## Request

> Build tally in the tally project: a Python 3 command-line tool that counts word frequencies in one or more text files or standard input and prints the most frequent words with their counts. It needs --top N (default 10), --ignore-case, --json for machine-readable output, --help, exit code 0 on success and 2 on usage errors, unit tests that run with python3 -m unittest, a README with usage examples, and no third-party dependencies.

No workflow was named, no model or effort was named, and nothing in the request mentions Orchflows.

## Against the skills and docs

What the skills and `docs/firstmate.md` ask for, and whether the primary did it unprompted:

- **Dynamic workflow as the catch-all.** Yes. It loaded the skill first and named the phases of the plan to the captain.
- **Model and effort per assignment as explicit spawn flags**, resolved from the request, then the saved workflow, then `crew-dispatch.json`. Yes, for both spawns, and it told the captain which model each agent ran on.
- **One fresh maker, one fresh reviewer who did not make it, one repair pass, no second review.** Yes, and it said so.
- **Brief wording** from the fold-in: identity line, "do not delegate", exact candidate ref and detached checkout, reviewed SHA at the top, "may run the tests", Make and Review sections by absolute path, commit before reporting, the local-only definition of done. Yes; the briefs follow the documented wording almost verbatim, which shows the primary read the updated doc before dispatching, as the `captain.md` block asks.
- **Repair steer** naming the report, the repairs, the deferred findings and a fresh `done:` line. Yes.
- **Backlog note with workflow, phase, task IDs, refs and guidance.** Yes, updated at every phase, on both the request item and the scout item.
- **Reviewer closed through FirstMate's completion gate; report retained.** Yes.
- **Delivery through the project's mode and merge authority.** Yes: held for the captain, merged with the guarded owner after approval, torn down after landing.
- **Codex first-run trust prompt.** Handled by the primary from the adapter reference.
- **Captain-facing language.** Outcomes and consequences, no task IDs, paths or status prefixes, apart from model names and effort levels, which the `captain.md` block makes the captain's own vocabulary.

What it did not do, or did differently:

- It selected only the `code` guidance domain. The README was written and reviewed without `writing` guidance; the reviewer still executed every README example. A captain who cares about prose can name the domain in the request.
- It confirmed each fresh worker with a foreground `sleep` and peek before ending the turn, which FirstMate's contract allows for "confirm the worker is processing the brief"; all later waiting went through the Stop-hook watcher.
- The review spawn printed FirstMate's "queued wakes pending" warning because the maker's done wake had been drained but not yet acknowledged; the acknowledgement followed the spawn. Harmless here, but the ordering is the primary's, not the skills'.
- It never ran the candidate's tests itself before or after the review, relying on the reviewer's run and the maker's repair report. That matches "the coordinator never edits a project" and FirstMate's read-only rule; the captain approved on the primary's summary.
- The hooks-review prompt that Codex 0.154 raised in the first trial did not appear. Since then the attribution in that record has been checked: nothing under FirstMate's `bin/` writes a `.codex/hooks.json` into a worktree, and the trusted hashes the earlier acceptance left in the operator's Codex configuration name the operator's own global hooks file. The prompt was about those hooks, trusted once and never asked again, which is why no later Codex worker saw it.

## Compared with the first trial

The human-driven captain of the first trial wrote longer briefs with numbered checklists and named more guidance domains. The model-driven primary wrote shorter briefs with the same structure and the same safety lines, chose the same delivery placement, and used FirstMate's decision hold for the merge approval where the first trial's captain approved in its own head. Both reviewers found one real defect outside the maker's own checks; both repairs landed by steer in one pass.

## Gaps

- One run, one primary model. A Sonnet or Codex primary has not been tried.
- Only `local-only` delivery and only the dynamic workflow. A saved workflow run by name, and `direct-PR` or `no-mistakes` placement, are untried through a model primary.
- The primary's cost was not recorded; the session ran interactively.
- The lab viewer started from a detached shell had to be signalled by hand before `fm-herdr-lab.sh teardown` would run; the helper's own `viewer stop` could not see a viewer it did not start in the same process tree.
